# 设计决策

## ADR-1：strict 模式让编译器写 SQL，不让模型写

**决策**：严格模式下 SQL 由 `builders.py` 从指标契约编译，模型完全不参与。

**理由**：口径一致性是结构问题。模型生成即使做到 99% 正确，剩下 1% 的漂移在企业里就是"这个月复购率为什么和上月不一样"的会议。编译器可以做到 100%，因为它是确定性的。

**代价**：只能回答已注册指标的问题。新增指标需要写 YAML + 一个 builder 函数。

---

## ADR-2：保留 exploratory 模式，但共用同一套策略

**决策**：探索性查询允许自由 SQL，但必须过 AST 审查与口径核对。

**理由**：真实分析不可能全部塞进指标目录。完全禁止会把用户推回 Excel，那才是真正的治理失败。

**代价**：exploratory 的结果口径不可保证，所以响应里 `metric` 可能为空，调用方需要自己判断可信度。

---

## ADR-3：口径核对只做弱校验

**决策**：核对聚合函数集合 + 必需过滤条件（如剔除退款），不做 SQL 等价性证明。

**理由**：SQL 等价性一般不可判定。做一个"看起来很深"的等价性检查，只会给出虚假的安全感。明确说"这是弱校验"，使用者才知道该在哪里补人工复核。

**代价**：两条语义不同但聚合相同的 SQL 可能都通过。

---

## ADR-4：PII 在执行前拦截，而不是靠提示词

**决策**：AST 检测敏感列，命中即拒绝；返回层再做掩码。

**理由**：提示词是建议，AST 是控制。`SELECT phone` 不会因为 system prompt 写了"注意隐私"就消失。

**代价**：需要维护敏感列清单；列名变更时要同步。

---

## ADR-5：不接模型也能跑

**决策**：`fake`/规则匹配作为默认路径，模型是可选组件。

**理由**：作品集要能被任何人 clone 下来跑通；生产系统也不应该把"能不能用"绑在一个外部 API 上。

**代价**：自然语言理解能力有限，只能匹配预置关键词。真正接入模型时，探索模式的召回会显著提升，但治理层不变。
